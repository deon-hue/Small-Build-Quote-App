# Small Build Company — Claude Code Instructions

## Phase Structure (REQUIRED — do not change without explicit instruction)

The quote builder uses a two-level hierarchical phase structure that is **job-type dependent**.

### Hierarchy
```
Main Phase (parentPhase)  e.g. "Phase 3 – Structural Shell"
  └── Sub-Phase (phase)   e.g. "External Walls & Blockwork"
        ├── 🔨 Labour
        ├── 📦 Materials
        ├── 🚜 Plant Hire
        ├── 👷 Subcontractors
        └── 📋 Other
```

### Job Types and Their Phase Templates
Each job type has its own default template in `lib/utils.ts` → `JOB_TEMPLATES`:
- **Rear Extension** — 10 main phases, ~30 sub-phases
- **Side Extension** — 10 main phases, ~26 sub-phases
- **Loft Conversion** — 9 main phases, ~20 sub-phases
- **Full Refurbishment** — 10 main phases, ~20 sub-phases
- **Kitchen Extension** — 11 main phases, ~25 sub-phases
- **Kitchen Fit-Out** — 6 main phases, ~14 sub-phases
- **Bathroom Fit-Out** — 6 main phases, ~13 sub-phases
- **Garden Room** — 7 main phases, ~15 sub-phases
- **Landscaping** — 9 main phases, ~17 sub-phases
- **New Build** — 13 main phases, ~28 sub-phases
- **Other** — 7 generic main phases

### Data Model
- `QuotePhase.parentPhase?: string` — main phase group name
- `QuotePhase.phase: string` — sub-phase / category name
- `QuoteItem.itemType` — one of: `'labour' | 'materials' | 'plant' | 'subcontractors' | 'other'`
- `QuoteItem.subcontractors?: number` — specialist subcontract cost
- `QuoteItem.other?: number` — fees, provisional sums, miscellaneous

### Template Helper (`lib/utils.ts`)
```typescript
tp(parentPhase, subPhase, labour, materials, plant, subcontractors=0, other=0,
   labourNotes='', materialsNotes='', plantNotes='', subNotes='', otherNotes='')
```

### AI Generate Phases (`app/api/generate-phases/route.ts`)
The AI prompt asks for `parentPhase`, `phase`, plus all five cost fields per sub-phase.
Response is mapped directly to the typed item structure.

### Rules
1. Every new phase created (via template, AI, or "+ Add Phase" button) must auto-generate all 5 typed rows
2. Legacy saved quotes (3-row format) are auto-converted to 5 rows on load
3. The user can add/edit/remove/rename main phases and sub-phases independently without changing the master template
4. Cost tracking is per sub-phase, per cost type — never aggregate to a single number

## Assembly Calculators (REQUIRED for every new calculator)

Assembly calculators price a Back Office sub-phase from geometry (wall length/height, foundation, etc.).
Built so far: internal stud/metal/block partitions, external cavity walls, 100mm and 215mm blockwork,
timber garden room wall, dwarf wall, sleeper wall (block & beam floor), parapet wall, and the Roof phase's
structure, covering and gutters. Every new one follows the same
pattern, and **is used from Take-off in the same way** — do not invent a different one.

**Electrics (`elec-install`) is the one calculator that is not drawn geometry.** It prices the whole electrical installation room by room,
per point at an electrician's all-in rate (`lib/electrics-units.ts` engine, `lib/electrics-description.ts`, `components/AssemblyElectricsDemo.tsx`).
Rooms start empty (added from a kind of room, which brings its usual points); a situation uplift % applies to points for the job or one room; a
special fitting (chandelier etc.) is an extra install line on top of its point, client-supplied or ours; a room can be priced by the day instead;
whole-house items (consumer unit, testing/certificate, circuits) are separate, only the certificate in the starting price. In Take-off (Electrics
phase) the ⚡ tool places electrical points on the plan (`lib/electric-points.ts`, `app/(app)/takeoff/components/ElectricalPointsPanel.tsx`): they are
**each point is drawn as its drafting symbol, not a dot** (`lib/electric-symbols.ts`, tested: a socket, a switch with its lever, a downlight as the circle with a cross, a pendant, a wall light, a batten, a cooker switch, an extractor fan, smoke, heat and CO alarms, TV and data points and the rest, 26 kinds; shapes in `lib/plumb-symbols.ts` form, 1 unit = 10mm, BACK at the top; the 'accent' parts take the point's group colour: sockets blue, switches violet, lighting amber, appliances green, safety red, data teal; the same `symShape` / `facingAngle` as the plumbing fittings, so a wall-mounted point turns its back to the nearest wall face within 800mm and a batten lies along it; sized a little above the real plate so it reads, never under about 16 screen pixels; the name, room and any special fitting show on hover, a special fitting keeps its star; a kind with no symbol keeps its dot): kept on ONE Take-off item (`electricsSummary`, id `electrics-summary`, holding `electricPoints`, the calculator's `electricsState` and its priced

  `suggestGableRoofLabour` in `lib/flat-roof-labour.ts`) — two rafter faces to a ridge, a wall plate + straps

  existing wall the way a lean-to does), and ceiling joists tying the rafter feet together across the full
  span; a new gable end wall is priced under External Walls, not here. Its rafter section reuses

  ceiling joists get a section picker but no span-chart check (a long span needs a binder or an engineer's
  design — noted, not modelled). No roof-window openings yet (mono-pitch's plan-view/trimmer pattern in
  `lib/mono-pitch-roof.ts` is ready to reuse there when asked). Each of the gable roof's two ends is
  independently `'gable' | 'existing-wall'` (`GableEndTreatment`), same real case as the hip roof's per-end
  treatment (a rear extension tied into the house at one end). Unlike hip, a gable end never got a wall-plate
  credit either way (that was already true before this — the new wall's own top plate is its own build's
  scope), so `'existing-wall'` only *adds* restraint straps tying the ridge and end rafters back to it — the
  default (both `'gable'`) case is priced byte-for-byte the same as before this was added, confirmed by
  re-running the original hand-test unchanged. Rafter/ridge framing is identical for either end treatment
  (the ridge always runs the full length on a gable roof, unlike a hip's). Hip structure is its own component,
  `AssemblyHipRoofDemo.tsx` (engine `lib/hip-roof.ts`, description `lib/hip-roof-description.ts`, labour
  `suggestHipRoofLabour` in `lib/flat-roof-labour.ts`) — common rafters along the ridge zone on the two long
  sides, four hip rafters at 45° from each corner to a ridge end, jack rafters filling each hip triangle, a
  wall plate + straps round the full perimeter (every wall is an eaves wall on a hip roof — no gable ends to
  price under External Walls here), and ceiling joists across the full length. If the span is at least as
  long as the ridge-direction length the ridge length comes out at zero — a pyramid hip, no ridge board, the
  four hips meeting at a single apex instead; the engine and screen both handle this without a special case
  breaking (`isPyramid` flag, checked everywhere a ridge would otherwise be priced or drawn). The roof surface
  is one uniform pitch everywhere (commons, hips and jacks all lie in the same sloped planes), so the slope
  area is simply the overhung plan area over cos(pitch) — no need to sum every rafter's own strip, and a
  cleaner formula than the flat/mono-pitch/gable roofs use, worth carrying back to them if they ever need it.
  A jack rafter shares its roof plane's pitch with the common rafters it's parallel to, so it uses the very
  same true-length formula, just with its own (shorter) distance in from the corner as the run; a hip rafter's
  own run is on the diagonal (a 45° hip, stretched by √2), reaching the same rise, so its length comes from
  Pythagoras rather than the roof's pitch angle directly. Only the common-rafter length is checked against the
  span chart; hip and jack rafters (and the ridge board) take the next timber size up, same convention as the
  ledger/kerb sizing elsewhere. No roof-window openings yet, same as gable.

  **Pitched roof covering** (`roof-covering`'s `pitched` family, `AssemblyPitchedRoofCoveringDemo.tsx`, engine
  `lib/pitched-roof-covering.ts`, description `lib/pitched-roof-covering-description.ts`, labour
  `suggestPitchedRoofCoveringLabour` in `lib/flat-roof-labour.ts`) is a different pattern from every other
  covering/structure calculator: `lib/pitched-roof-covering.ts` itself is roof-shape-agnostic — it only takes
  already-worked-out edge lengths (slope area, ridge/hip/verge/abutment/eaves lm) and adds the one covering-
  specific number, the batten run (`slopeAreaM2 × 1000 / gaugeMm` — an area/gauge identity that holds for a
  hip's trapezoidal faces too, not just a plain rectangle, since a batten course's length is proportional to
  local face width and courses are evenly spaced). Which roof type (mono/gable/hip) and which per-end choice
  gives which edge lengths is worked out by the **screen**, calling `calculateMonoPitchRoofGeometry`/
  `calculateGableRoofGeometry`/`calculateHipRoofGeometry` **directly at runtime** — screens have no
  type-only-import restriction, only `lib/*-description.ts`/`lib/*-labour.ts` modules do, so this is fine and
  reuses the already-tested structure trig rather than re-deriving it a third time. The mapping: a ridge only
  exists for gable/hip; a hip cap follows the hip rafters' own line (`hipRafterLm`, reused directly); a verge
  runs up the slope (the true rafter length) at any new-wall gable end, or a hip's non-hipped `'gable'` end;
  an abutment (lead flashing) runs wherever the roof meets an **existing** wall instead — always at a
  mono-pitch's high wall (whichever way it's fixed there), or any gable/hip end set to `'existing-wall'`;
  eaves are simply wherever the structure's own geometry credits a wall plate (`wallPlateLm`, or `lengthM` for
  mono's one low wall) — "eaves" and "gets a wall plate" are the same thing in every one of these engines, so
  it's reused rather than re-derived. If a future covering calculator needs the same shape-agnostic-engine
  pattern, this is the one to copy — not the structure calculators' own self-contained-engine pattern. Each of the hip roof's two ends
  (along the ridge direction, not the long eaves) is independently `'hip' | 'gable' | 'existing-wall'`
  (`HipEndTreatment`) — a real case: hipped at the garden end, tied into the house at the other. A gabled or
  existing-wall end gets no hip/jack rafters at all (the ridge and common rafters simply run the full way to
  it, exactly like a gable roof's), and only an existing-wall end skips the wall-plate credit there (nothing
  new is built — still gets restraint straps back to it, same as every other end). Both ends non-hip and the
  ridge runs the full length, same numbers a gable roof would give for that length/span — a good consistency
  check when extending an engine like this. `isPyramid` only applies when *both* ends are `'hip'` and the
  ridge would go to zero; a single hip end reaching zero (too short a length for even its own half-span) is a
  different, genuine problem, warned separately. `roof-structure`'s "Include fitting the rooflights" optional
  labour line points the estimator at `roof-rooflights` instead of duplicating it — a new calculator that also
  fits something another one prices should do the same, not silently double-count. `roof-structure` pairs with
  the `cold_flat_roof`/`warm_flat_roof` Build-Up Types (flat only so far); the others appear under
  "Calculators". A roof is sized from the bounding box of the drawn shape via `drawnBoxMm`, passed as
  `externalLengthMm` + `externalWidthMm`, and the panel card shows "Size" not "Length" — `roof-rooflights`
  ignores both (it has no drawn geometry; any small shape drawn for it is just a placemarker). A calculator
  for any other phase (floors, plastering, ...) needs
  `resolveBuiltAssembly`, the properties panel's Build-Up Type/sub-phase picker, the `hideForBuiltAssembly`
  flag, and the carry-over extended to that phase — do it the same way, don't fork a new pattern.

## Take-off sheets: several plans in one take-off (REQUIRED if you touch `app/(app)/takeoff/page.tsx`)

Each plan loaded in Take-off is a SHEET (`TakeoffSheet` in `lib/takeoff-types.ts`, rules in `lib/takeoff-sheets.ts`, tested): its own picture, its own scale and its own drawings; one job-wide schedule and total, with a sheet filter and a sheet tag on each item (`drawingRef` is set to the sheet name once there are two or more). `project.calibration` is ALWAYS the showing sheet's scale, so every measurement in the page keeps working unchanged; `switchActiveSheet` swaps it. A drawing (`DrawnElement.sheetId`) and an electrical point (`ElectricPoint.sheetId`) belong to the sheet they were drawn on; one with no `sheetId` belongs to the first sheet, and adding the first plan stamps whatever is already drawn. RULES: draw and show only `elementsOnActiveSheet(project)` (and points that are `onActiveSheet`); a scale change must remeasure ONLY the showing sheet's drawings (`rescaleActiveSheet` / the `onlyElementIds` argument of `recalcItemsForMpp`: every other sheet has its own scale, so a global remeasure silently corrupts them); picking an item on another sheet must switch to its sheet (`switchSheet(id, true)`). The picture of each sheet is NOT in the project: it is kept in IndexedDB (`lib/takeoff-sheet-images.ts`, key project id + sheet id) because localStorage holds ~5MB (one big plan filling it used to stop the whole take-off saving) and is not part of the cloud row. Each picture ALSO has a copy in the account (`lib/takeoff-sheet-cloud.ts`): the existing private `quote-documents` bucket, path `{user_id}/takeoff-{project_id}/{sheet_id}.pic` (its policies already allow your own folder, so no new setup; 10MB a file, so a bigger picture is squeezed to JPEG first; no UPDATE policy, so a picture is replaced by remove-then-upload). The copy is made in the background when a plan is added (`savePictureToAccount` in Take-off, never blocking drawing), plans from before are put there once when the take-off is open, and a sheet tab shows ☁… / ☁✓ / ☁⚠ (press to retry). The image-load effect reads this device first and falls back to downloading from the account, caching it on the device, so a take-off opens with its plans on any computer; the "picture is missing" banner now only shows when neither place has it. Deleting a take-off from My Take-offs removes its folder of pictures (deleting a single sheet leaves its picture, so Recovery still works). The cloud row has no sheets column: they ride inside the existing `calibration` JSON (`lib/takeoff-sync.ts`), so no SQL is needed. A take-off from before sheets (one plan inside the project) is moved into 'Plan 1' on first load; a sheet whose picture is not on this device shows a banner and 'Add Plan' fills THAT sheet (keeping its drawings and scale). A multi-page PDF asks which pages to use and makes a sheet of each. **Every place that opens a PDF with pdf.js MUST pass `...pdfjsResources(pdfjsLib.version)` (`lib/pdfjs-resources.ts`) to `getDocument`** (Take-off `loadPlanFile` and `components/DocumentPreviewPane.tsx` do): pdf.js 5 reads black-and-white scans (CCITT fax or JBIG2, what most scanners make, e.g. an Epson Scan PDF) and JPEG 2000 pictures through wasm files it is given by `wasmUrl`, and without it the page renders completely BLANK WHITE with only a console warning ('Ensure that the `wasmUrl` API parameter is provided'), so the sheet is made, saved to the account (cloud tick) and shows no plan (found 2026-10-29 on a scanned 4-page A4 plan: 0.00% dark pixels before, 4 to 8% after). The helper also gives the standard fonts, character maps and colour profiles, all from unpkg at the installed version like the worker. A1 at 1:50 covers 42 x 30 m. There is no snapping grid or paper edge other than a thin border; the Grid toggle works as on any plan. Deleting a sheet removes its drawings, items and points (a recovery copy is kept). **Scale presets** (1:20 to 1:500, `lib/takeoff-paper.ts`, tested) work out metres per pixel from the PAPER: a pixel is some mm of paper, times the scale. A PDF page is drawn at 2x (144 px to the inch) so a PDF pixel is always `PDF_RENDER_MM_PER_PX` = 25.4/144 mm of paper whatever the sheet size; the sheet records it (`paperMmPerPx`, `paper`), and an older sheet or an image the size of an A-size PDF page is inferred (`inferPdfPaper`). ## A calculator's size carries back to the Take-off drawing (REQUIRED for a new drawn-size calculator)

A calculator is sized from the drawing (a line's length, a roof's box, a floor's area) and, when the estimator types a different size inside it and presses Save & Price, the DRAWING is scaled to match so the quantity, label, area and schedule agree (it used to change only the price). `CalcScope` (`components/calc-state.tsx`) stamps each state namespace as it is written and hands the save handler `size` (`CalcSize`, `sizeFromValues` in `lib/calc-size.ts`): the namespace with a `lengthMm` or `areaM2` written most recently (a roof switched between types leaves the old type's values behind), reading `lengthMm`, `widthMm` (or `spanMm`: gable, hip, mono-pitch and pitched covering call their width a span) and `areaM2`. In Take-off's `renderAssemblyPanel` onSave, `planResize` / `applyResize` scale the item's element by what kind of drawing it is: a LINE by its length from its first point, a BOX (roof, raft: `isBoxShape`) so its bounding box becomes the calculator's length and width (the long side stays the long side), a FLOOR (`isFloorShape`) evenly to the calculator's area; then `recalcItemsForMpp` re-measures that one item and a toast says what changed ("8.00 × 4.88 m → 10.00 × 4.88 m"). Within 0.2% nothing moves. So a new drawn-size calculator must keep its drawn size in a `useCalcState` named `lengthMm` (and `widthMm`/`spanMm`) or `areaM2` to take part. Not covered: the tiling and other room-by-room calculators (their sizes live inside rooms), calculators that take no drawn size (Wall Removal, Render and Wall Insulation keep their length in a list of walls), and the electrics path.

## Walls drawn at their real thickness, layer by layer (Take-off & Draw)

A wall in External Walls or Internal Walls & Partitions is painted architecturally: a band at its REAL thickness to the plan's scale, made of its layers in the usual conventions (facing brick = red diagonal hatch, block = grey dots, insulation = yellow zig-zag, cavity = white, timber = brown cross, boards and render thin), labelled in its tag ("300 cavity", "215 solid block", "100 stud partition"). Pure module `lib/wall-drawing.ts` (tested): `wallSpecForItem` in `app/(app)/takeoff/page.tsx` decides WHAT the wall is, in this order: (1) its saved calculator (`assemblyCalcState`: the cavity wall's outer leaf, cavity, insulation and inner leaf via `cavityWallSpec`; a solid block's width or flat 215 via `solidBlockSpec`), (2) its Build-Up Type's own layers (`allWallMakeups`: the live Back Office wall type, read by `specFromMakeupLayers`, which sorts layers into kinds by their names and gives a partial-fill layer the 25mm air gap a real cavity has), (3) the standard for its sub-phase (`defaultWallSpec`, a cavity wall with nothing else known being drawn INSULATED as the calculators start: full fill is brick + 100 mineral wool + block, partial fill is brick + 75 PIR + 50 air gap + block; a saved calculator's own `boardThicknessMm` sets the PIR thickness and the rest of the cavity is the gap; checked by eye on a sheet of every wall type 2026-10-28: stud, metal stud, block partition, 100/215 blockwork, timber garden room, dwarf and sleeper walls), else, for a PARTITION only, its older Construction type (`constructionWallSpec`: block 100/140, half and full brick, metal stud 70/100, timber stud, each with board on both faces; metal stud 70 to start, as its Properties show; existing wall and drylining have nothing to draw), else nothing and the old fixed-pixel band is used. **An outside wall switched to a calculator AFTER it was drawn** (the 'Calculators' group of the Build-up Type list, which sets `taskSubphaseId` and leaves the old `floorMakeupId` on the item) is drawn as that calculator, not as the Build-up Type it started with (`calculatorOverridesMakeup` in `lib/wall-drawing.ts`, tested: a calculator sub-phase picked that is not the one paired with the item's Build-up Type wins over the Build-up Type's layers, so a wall first drawn as the default cavity wall and then set to Solid Brick Wall (Victorian) shows 330 solid brick, a 215 block wall 215 solid block, and back to a cavity Build-up Type 300 cavity; before this every such wall kept drawing as the cavity wall it was drawn as). **A stud partition (`iw-stud-partition`, `iw-metal-stud`, `AssemblyWallDemo`) is drawn from what is set in its calculator** (`studWallSpec` in `lib/wall-drawing.ts`, tested; read from the saved `AssemblyWallDemo` state when it was Saved & Priced, else the way the calculator starts): the plasterboard on BOTH faces or ONE (`layerSides.lining`; the calculator's lining now starts on both faces, it used to price one side only), and between the studs the insulation chosen (`insulationType`: acoustic mineral wool, glass mineral wool or PIR board, `STUD_INSULATION_TYPES`; `insulationMm` 25, 50 or the stud depth, held to the depth of the studs, 70mm metal / 89mm timber; the unfilled depth is drawn as air; "None" is the `insulation` line switched off, the same as its tick in the breakdown, and then the studs themselves are drawn). The controls are in the calculator's "Plasterboard and insulation" section; the insulation line is named and priced from the kind and thickness (sample price per m2 at 50mm: 8.50 / 5.20 / 14.00, scaled by thickness, a typed rate wins). The drawing only follows once the calculator is saved (Save & Price), as for the cavity wall. **A partition with no Sub-Phase picked is drawn as the FIRST sub-phase in the list**, the same one its Properties and calculator already show (`intSel` in `wallSpecForItem`; it used to be a plain line until a sub-phase was picked, which looked as if the wall had no thickness). An external wall with no type picked shows the first type, as the Properties panel does. WHERE it sits: external walls take the line you draw as the OUTSIDE face and build to the inside (the right of the way you drew; for a rectangle or polygon outline towards the middle, whichever way round it was drawn; "⇄ Flip to the other side" in Properties, `wallFlip`, for an open line drawn the other way); internal walls are centred on the line. `wallDrawing` gives each layer as an SVG path (mitred corners, two rings for a closed outline, fill-rule evenodd); the screen paints them in `renderElement` (after the layer is wide enough on screen, 3px, the hatching shows; narrower it is a plain tinted band), a white halo behind in `renderHalo`, and the hatching patterns are `wl-*` in the SVG defs (scaled by 1/zoom so they stay the same density). Quantities are unchanged: they still come from the drawn line's length (the outside face for an external wall). **Where walls meet** (`chainWalls` in `lib/wall-drawing.ts`, tested; painted by `renderWallVisuals`, which paints ALL the walls after the element loop with pointer events off, while `renderElement` keeps only each wall's clicking path): walls of the same group (external/internal, reference, and the same layers) whose ends meet within 3 plan pixels (snapping makes them exact) are one run with mitred corners, a flipped wall being taken from its other end so the inside is always to the right, and a run that comes back to its start is a closed ring (four separate walls round a house paint as one ring, built inward). **Near corners are painted as corners** (`reachPx` on a `WallPiece`, set by `renderWallVisuals` and `wallSolids` to 1.5 wall thicknesses, tested): two open walls of the same make-up whose ends stop SHORT of the point where their lines cross (up to 1.5 thicknesses away: a gap, or a wall drawn to the face of the other), or run PAST it (an overshoot, up to HALF that), are painted as meeting exactly at that crossing, so the skins (brick, insulation, inner block) run continuously round the corner instead of one wall butting into the other; a wall that carries on well past the crossing is a tee and is left alone, as are walls too far from the crossing, parallel walls and walls of different make-up. Only the PAINTING (and the room finding, which uses the same chains) changes: the walls' own lines and lengths are not, and the Join Corner tool makes the geometry itself exact. A wall ending on the SIDE of another is not joined: internal walls are painted first and external over them, and within a kind the longer wall over the shorter, so a partition stops at the face of the wall it butts into (the clean look of a T-junction). The selected wall's blue dashed outline is painted last, over everything. **Corners between walls of DIFFERENT make-up** (a brick-faced wall and a rendered one, a different cavity width: `mitreCuts` and the `cuts` option of `wallDrawing` in `lib/wall-drawing.ts`, tested; `cornerCuts` in Take-off, used by `renderWallVisuals` and `wallSolids` so the painting and the room finding agree): two runs of the same kind (outside or inside) whose ends meet (or stop short or run past by up to the same reach as a same-make-up corner) cannot be one chain, so each is moved to the corner and every layer line of it ends on ONE mitre line through the outer corner and the inner corner (where the two inner faces meet, found from each run's two faces, `wallBand`), so one wall's layers stop exactly where the other's begin, with no overlap and no gap whatever the two thicknesses (checked on the live screen: 0 overlapping and 0 uncovered points in the corner). A wall ending on the side of another (a tee), or an inside wall meeting an outside one, is not cut. **An outside wall that is not part of a closed ring still gets an inside** (`wallDirOverride`): a run that turns round (a U or an L, as when a wall is taken out upstairs) has its inside on the side it turns towards, and an outside wall on an upper level that lies along an outside wall of the level BELOW is built to the same side as that wall; only a lone wall with neither is painted to the right of the way it was drawn (before this, a first floor drawn or copied anticlockwise and then opened up was painted OUTWARD, sticking out past the ground floor by a wall thickness: checked 189,88 to 600,361 before and 200,99 to 600,349 after, against the outline 200,99 to 600,349). **Which side is inside does not depend on the make-up or on a flip** (`wallDirOverride`, `paintFlip`): a closed run of sides is found from how the walls were DRAWN, whatever each side is made of and ignoring any flip, so every side of the ring builds INWARD even when one is brick-faced and another rendered (a different make-up used to break the ring, and the sides then built outward if the house was drawn anticlockwise); a flip then turns only the one wall over (**⇄ Flip wall** in the Aids toolbar, the F key or Properties, an outside wall drawn as a line; a partition is centred on its line so has nothing to flip). **One wall per side**: a wall drawn as one run (three clicks or more with the Line tool: the U of an extension) is split into ONE WALL PER SIDE when it is finished in External Walls or Internal Walls & Partitions (the 'Each side of a wall is its own wall' tick under the tools, kept per browser as `splitWalls` in `sbc_takeoff_view`, on by default), so each side is its own drawing and its own Take-off item that can be clicked, edited, priced with its own calculator and doors and windows, and deleted; because walls of the same make-up whose ends meet are painted as one run (`chainWalls`), the drawing looks the same. An existing wall drawn as one run (or a rectangle or polygon wall) is split from its Properties ('✂ Split into N separate walls', `splitWallSides`, undoable): `lib/wall-split.ts` (tested) gives the sides (`sidesOf`: a rectangle's two corners become four sides, closed) and moves the placed doors and windows onto the side they were on (`splitOpenings`); each side keeps the wall type, height and sub-phase, the typed openings go to the first side, and the saved calculator and its price are CLEARED (the length has changed, so each side must be opened and Save & Priced again; a calculator's own settings start from the wall type again). A single two-point line is never split, and walls drawn before this change stay as they were until split. Not built yet: doors and windows in the band, rooms made from the walls, and a printed plan; timber frame and other wall calculators use the build-up layers or the sub-phase standard, not their own sizes.

## Rooms made from the walls (Take-off & Draw)

Rooms are FOUND, not drawn. `lib/rooms-from-walls.ts` (pure, tested) `detectRooms` fills in every wall (the rings of `wallDrawing(...).rings`, joined where walls meet exactly as they are painted, `wallSolids` in Take-off) AND the gap of every placed door and window (so an opening never joins two rooms) on a 10mm grid (bigger cells only for a huge drawing), then the empty space that does not reach the edge is a room: its outline (cell edges walked round and simplified, so a rectangle is four corners and an L six), floor area (cells, less a column or chimney breast standing in it), the length of wall round it, the box it fits in, and where its name goes (the roomiest cell). A room is only found if its walls make a closed space: a gap shows as no room, and the Rooms panel says so. Rooms are re-found 250ms after the last change to walls, items or openings (not on every mouse move of a drag) and only while shown (the Rooms tick in the view box top right, the 🏠 Rooms tool, or a calculator open), and ignored if the sheet has changed meanwhile. The doors and windows that open into each room are counted by looking 150mm beyond each face of each opening (a door between two rooms counts in both).

**Drawn rooms**: a room with no walls round it can be DRAWN as a shape: with the Rooms tool on, pick Rectangle or Polygon in the tool list (or the 'Draw a room' buttons in the Rooms panel; typed sizes like 4.5x3 work as for any rectangle) and `finishElement` hands the outline to `addDrawnRoom` instead of making a priced drawing (`roomDraw`, reset whenever the tool is not rectangle or polygon). It is stored as a `DrawnRoomShape` (just the outline) in `TakeoffSheet.roomShapes` (on the project, `TakeoffProject.roomShapes`, before there is a sheet; both moved onto the first sheet by `addSheets`, and carried in the cloud `calibration` meta) and joins the rooms found from walls (`roomFromPolygon`, `sortRooms`; a drawn room has `drawnId`, no openings are counted for it unless a placed opening happens to sit beside it, and it can be deleted from the panel; it can be MOVED (drag it by its middle with the Rooms tool on), RESHAPED (drag a white corner of the selected room; a rectangle, `DrawnRoomShape.rect`, stays a rectangle, held to the opposite corner, and the corner snaps like any drawn point) or RESIZED by typing its width and depth in the panel (its top-left corner stays); the pure rules are `moveOutline`, `rectFromCorners`, `resizeRectOutline`, `isAxisRect` and `labelAfterEdit` in `lib/rooms-from-walls.ts` (tested), and the room's name point moves with it (or is brought back inside if a reshape leaves it outside). Drawn rooms are added to the room list fresh on every render (`roomData`), while the rooms found from walls come from the debounced `roomCore`, so dragging one is smooth. Moving and resizing drawn rooms is not part of undo). A shape drawn with an ordinary phase's rectangle tool (Floors & Screeds, etc.) is NOT a room. **Room edges**: a ROOM EDGE is a line that closes a room where there is no wall (the open side of three walls, an extension against the existing house) or splits an open-plan space into rooms; it is not a wall, so nothing is painted, priced or counted for it. With the Rooms tool on, pick Line in the tool list (or 'Room edge' in the panel; `roomDraw` is `'room' | 'edge' | false`) and click its start and end (double-click to finish; a bent edge works). It is stored as a `RoomEdge` (a list of points) in `TakeoffSheet.roomEdges` (project-level `roomEdges` before there is a sheet, moved onto the first sheet by `addSheets`, carried in the cloud meta like `roomShapes`), shown dashed purple with the rooms, and passed to `detectRooms({ edges })`, which fills each segment in as a strip one and a half cells wide AFTER the cell size is known (so it always closes the gap, even slanted; it takes about 15mm of floor along its length) and includes it in the drawing's box; edges alone make no room, they only close what walls make. Click an edge with the Rooms tool to select it; Delete or the panel's Delete removes it. **A drawn room that walls now surround is left out** (`roomData.coveredDrawn`): a drawn room whose name point is inside a room found from walls (or the other way round) is the same room twice, so the room the walls make wins (measured between the wall faces), the drawn piece is dropped from the list, the plan labels and the calculators, and the Rooms panel says so with a button that removes the leftover outlines (the names stay: they belong to the rooms the walls make). **An edge also CUTS A DRAWN ROOM** (`splitDrawnRoom`, `edgesTouch` in `lib/rooms-from-walls.ts`, tested): a drawn room crossed by room edges (right across it, or a line between two corners of its outline, such as the line between the two blocks of an L) becomes the pieces the edges make of it, each a room that can be selected, named and fed to the calculators; the outline and the edges are filled in as thin strips and the enclosed space found (`detectRooms` with `edgesMakeRooms`, which gives the strips' half-width back to each piece's area), only when an edge actually touches the room and makes two or more pieces (otherwise the exact outline is used); each piece keeps the shape's `drawnId`, so moving, reshaping, resizing (the whole rectangle) or deleting acts on the drawn shape and every piece's name goes with it (`editDrawnShape` moves EVERY name inside the old outline); the shape's grab area and corner handles are the shape's, drawn from `roomShapesOf`, not each piece's. The edges do not move when the shape is moved. Edges cannot yet be moved or reshaped (delete and redraw). **Names** are `RoomLabel`s on the SHEET (`TakeoffSheet.roomLabels`, so they ride in the calibration JSON like the sheets, no SQL, and go with a deleted sheet): a name, a kind (`ROOM_KINDS`), a ceiling height (2.4m when not given), anchored to a POINT inside the room, so it follows the room if the walls change; the room that contains the point has the name (the first, if several). Unnamed rooms are "Room 1..." with an id from where they are. Naming is not part of undo. The 🏠 Rooms tool (any phase) selects a room by clicking inside it and opens `app/(app)/takeoff/components/RoomsPanel.tsx` (list with area, size, wall length, doors and windows; name, kind, height; wall area less openings). A point placed in the Electrics phase takes the name of the named room it falls in (`electricRoomShapes`).

**Handing rooms to the by-room calculators**: `PlanRoomInfo` (`describeRooms`) goes to the calculator as the render option `planRooms`; `components/PlanRoomsBar.tsx` shows them at the top of the calculator's rooms (press one to add it, or Add all); a calculator room made from one carries `planRoomId` and `planRoomSig` and FOLLOWS the plan (`followPlanRooms` in `lib/rooms-merge.ts`, tested: refit only when the plan's room changes, so what was typed stays; a room whose plan room is not found is left alone, never dropped or detached). Built so far: Internal Plastering & Boarding (by room) (floor and wall length from the true area and perimeter, `sidesFromAreaPerimeter`; height, doors, windows; the wall and ceiling areas overridden with the drawn ones) and Floor Tiling (by room) (an 'other' shaped room with the true area and perimeter, so an L-shaped room measures right, and its doors). Kind maps are `plasterKindFor` and `tilingKindFor`. Also fed the same way now: **Tiling Preparation** (true floor area and wall length as an 'other' shape, height; the wall areas to prepare start as the kind's usual ones; a shower room's floor is tanked), **Electric Underfloor Heating** (true area and wall length; the heated area is that less fixed things and the margin), **Wall Tiling** (name, true ceiling height and the kind's usual tiled areas: the plan cannot say which walls are tiled, so the areas are still set in the calculator and only the height follows the plan) and **Internal Decoration** (as plastering: size from the true area and perimeter, height, doors, windows, drawn wall and ceiling areas). **Strip-Out by Room** (floor area and height from the plan; what is taken out starts as the usual for that kind and size, and when the plan's room changes the items still at the usual for the OLD size move to the usual for the new one while any count you typed stays; `stripKindFor`) and **Plumbing Installation (by room)** (the name and kind with the kind's usual fittings only: a plumbing room's fittings do not depend on its size, so it remembers `planRoomId` but has nothing to follow; `plumbingKindFor`) are fed too. **Electrics** (`elec-install`) is fed too, beside its own point feed: the calculator takes `roomsOnPlan` (the `planRooms` render option) and shows the bar; a room added from it has the room's name and the usual points for its kind (`electricsKindFor`) and is tied to the plan by name (`planName`, `planRoomId`), so points placed on the plan in a room of that name COUNT IN it (their counts replace the usual ones for those kinds of point, no duplicate room is made) and a room already made by a placed point is shown as added. A point placed in the Electrics phase takes the name of the named room (found or drawn) it falls in. NOT yet fed: rooms across more than one sheet (rooms work on the showing sheet only). For any further by-room calculator add the same three pieces: a `planRoomId`/`planRoomSig` on the room type, an add function and a follow effect, the bar.

## Files on the contact card (customer files, quote and job files, zip download)

A client's contact card (`app/(app)/clients/page.tsx`, clients only) has a Files section (`components/ClientFilesSection.tsx`). It lists, in folders: **Customer files** (added to the contact itself: table `client_files`, `supabase/client-files.sql` with its undo, files in the existing private `job-documents` bucket under `<user>/clients/<contact>/…`, helpers in `lib/client-files.ts`, 50 MB each), then each of the customer's **quotes** (read from `quote_documents`, bucket `quote-documents`) and **jobs** (read from `job_attachments`, bucket `job-documents`): those are READ, never copied, so they use no extra space, and they are added/removed in the quote or job itself. The customer's quotes and jobs are the ones the card already matches by name (`getClientQuotes`/`getClientJobs`; deleted quotes left out). Each file has View and Download; each folder and the whole customer have a zip download: `lib/zip-store.ts` writes an UNCOMPRESSED zip in the browser (plans and photos are already compressed; zip32, so refuses over 3.5 GB and asks first over 1 GB; tested against Windows' own zip reader), fetching each file with `storage.download`, laid out Customer name / Customer files, Quotes / <quote>, Jobs / <job>, repeat names numbered. Until `client-files.sql` has been run the section says so for the customer's own files and still shows and zips the quote and job files. Deleting a contact first removes its files from storage (`removeAllClientFiles`, called in `deleteClient`) so no orphaned files use space. ## New database tables need explicit grants (REQUIRED, from 30 Oct 2026)

Supabase stopped automatically granting Data API access to new tables in the `public` schema on 30 October 2026. A table created without
grants returns "permission denied" to supabase-js and the app, which looks like a feature that silently won't save or load. So every SQL file that
`create table`s in `public` must, in the SAME file, also:
1. `grant select, insert, update, delete on public.<table> to authenticated;` and `... to service_role;` (add `grant usage, select on` any sequence it uses).
2. Grant `select` to `anon` ONLY if the table is meant to be readable when signed out. Most are not (nothing sensitive to `anon`). Decide per table.
3. Keep `enable row level security` and its policies as before: the grant opens the door to the API, the policies still decide which rows.
Tables created before 30 Oct 2026 keep their access, so old SQL files are left alone. `supabase/job-selections.sql` is a good example to copy.
If a database is ever rebuilt from the SQL files (new project, preview branch, `supabase db reset`), the older files that lack grants need a one-off pass first.
