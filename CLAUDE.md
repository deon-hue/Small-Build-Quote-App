# Small Build Company — Claude Code Instructions

## Phase Structure (REQUIRED — do not change without explicit instruction)

The quote builder uses a two-level hierarchical phase structure that is **job-type dependent**.

### Hierarchy
```
Main Phase (parentPhase)  e.g. "Phase 3 – Structural Shell"
  └── Sub-Phase (phase)   e.g. "External Walls & Blockwork"
        ├── 🔨 Labour
        ├── 📦 Materials
        ├── 🚜 Plant Hire
        ├── 👷 Subcontractors
        └── 📋 Other
```

### Job Types and Their Phase Templates
Each job type has its own default template in `lib/utils.ts` → `JOB_TEMPLATES`:
- **Rear Extension** — 10 main phases, ~30 sub-phases
- **Side Extension** — 10 main phases, ~26 sub-phases
- **Loft Conversion** — 9 main phases, ~20 sub-phases
- **Full Refurbishment** — 10 main phases, ~20 sub-phases
- **Kitchen Extension** — 11 main phases, ~25 sub-phases
- **Kitchen Fit-Out** — 6 main phases, ~14 sub-phases
- **Bathroom Fit-Out** — 6 main phases, ~13 sub-phases
- **Garden Room** — 7 main phases, ~15 sub-phases
- **Landscaping** — 9 main phases, ~17 sub-phases
- **New Build** — 13 main phases, ~28 sub-phases
- **Other** — 7 generic main phases

### Data Model
- `QuotePhase.parentPhase?: string` — main phase group name
- `QuotePhase.phase: string` — sub-phase / category name
- `QuoteItem.itemType` — one of: `'labour' | 'materials' | 'plant' | 'subcontractors' | 'other'`
- `QuoteItem.subcontractors?: number` — specialist subcontract cost
- `QuoteItem.other?: number` — fees, provisional sums, miscellaneous

### Template Helper (`lib/utils.ts`)
```typescript
tp(parentPhase, subPhase, labour, materials, plant, subcontractors=0, other=0,
   labourNotes='', materialsNotes='', plantNotes='', subNotes='', otherNotes='')
```

### AI Generate Phases (`app/api/generate-phases/route.ts`)
The AI prompt asks for `parentPhase`, `phase`, plus all five cost fields per sub-phase.
Response is mapped directly to the typed item structure.

### Rules
1. Every new phase created (via template, AI, or "+ Add Phase" button) must auto-generate all 5 typed rows
2. Legacy saved quotes (3-row format) are auto-converted to 5 rows on load
3. The user can add/edit/remove/rename main phases and sub-phases independently without changing the master template
4. Cost tracking is per sub-phase, per cost type — never aggregate to a single number

## Assembly Calculators (REQUIRED for every new calculator)

Assembly calculators price a Back Office sub-phase from geometry (wall length/height, foundation, etc.).
Built so far: internal stud/metal/block partitions, external cavity walls, 100mm and 215mm blockwork,
timber garden room wall, dwarf wall, sleeper wall (block & beam floor), parapet wall, and the Roof phase's
structure, covering and gutters. Every new one follows the same
pattern, and **is used from Take-off in the same way** — do not invent a different one.

**Electrics (`elec-install`) is the one calculator that is not drawn geometry.** It prices the whole electrical installation room by room,
per point at an electrician's all-in rate (`lib/electrics-units.ts` engine, `lib/electrics-description.ts`, `components/AssemblyElectricsDemo.tsx`).
Rooms start empty (added from a kind of room, which brings its usual points); a situation uplift % applies to points for the job or one room; a
special fitting (chandelier etc.) is an extra install line on top of its point, client-supplied or ours; a room can be priced by the day instead;
whole-house items (consumer unit, testing/certificate, circuits) are separate, only the certificate in the starting price. In Take-off (Electrics
phase) the ⚡ tool places electrical points on the plan (`lib/electric-points.ts`, `app/(app)/takeoff/components/ElectricalPointsPanel.tsx`): they are
kept on ONE Take-off item (`electricsSummary`, id `electrics-summary`, holding `electricPoints`, the calculator's `electricsState` and its priced
`assemblyResult`) so they save with the project, and `planRoomsFromPoints` turns them into room counts that feed the calculator
(`mergePlanRooms` in `lib/electrics-units.ts`: a count follows the plan until typed over). Do not add per-room sub-phases for it.

**Internal decoration (`deco-internal-walls`) is the second room-by-room calculator** (`lib/decoration-units.ts` engine, `lib/decoration-description.ts`,
`components/AssemblyDecorationDemo.tsx`). ONE calculator covers prep, walls and ceilings, woodwork (skirting, architrave, rails), doors and window frames; each
room is sized and each surface says its condition (new plaster / painted good / painted poor / wallpaper) and filling-and-sanding level, because that
changes the price (mist coat, sealer, stripping + steamer hire, filler). Lines and labour tasks are per room and per kind of work; the painter trade is
`'painter'` in `lib/flat-roof-labour.ts`. All rates and hours are samples to check against real jobs. Rooms start empty. In Take-off, Decoration is a task phase: an area drawn there with the Internal decoration sub-phase picked is only a marker and the
calculator card opens like the roof's (`isDecoCalc` in `app/(app)/takeoff/page.tsx`; an item that already carries a flat `taskId` stays a task item). Still to do:
Specialist Finishes and External Painting calculators (Deon unsure on specialist), the AI interview asking about wall condition and prep, and moving Floor
Finishes out of Decoration into an Internal Finishes phase (needs his real Back Office data first).

Its state is kept with `useCalcState` (not the electrics-style saved state). The wall's two faces come from `wallBand` in `lib/wall-drawing.ts` (the same rules as `wallDrawing`: an external wall's inside is the side it builds to; an internal wall's 'inside' is the right of the way it was drawn), or a plain band for a wall not drawn at real thickness. A swing is read as `WdSwing` says: in or out, hinged left or right as you see the door from the side you push it open from. Openings are kept on ONE Take-off item (`wdSummary`, id `wd-summary`, holding `placedOpenings`, the calculator's `assemblyCalcState` and priced `assemblyResult`, `wdPricedKey` to say when the plan has changed since pricing) exactly like the electrical points, so they save, undo and clear with the project; an opening whose wall is deleted is hidden and not counted (and returns with the wall on undo). The calculator is FED the plan's openings (`planOpenings` render option, `mergePlanOpenings` in `lib/wd-units.ts`, tested): each drawn opening is added with its kind's usual trims, follows the drawing (kind, size, swing, reference) when the DRAWING's opening changes and is otherwise left as typed (`planId`, `fromPlan`), one deleted on the plan goes, and an opening typed in the calculator with no drawing is never touched. **Centre and flip** (the selected opening's panel): '↔ Centre on the wall' puts it in the middle of the straight length it is on (`segmentMiddle`, tested); '⇄ Flip to the other side' turns it over: a swinging door gets the opposite swing with the hinge at the SAME end (`flippedSwing`: in and out swap and left and right swap), any other kind (a bay window, a bi-fold) gets `PlacedOpening.flipped`, which makes a bay project to the inside and a bi-fold fold the other way. **An opening is measured on the wall as it is PAINTED** (`wallDirOverride`, `wallPaintOpts` in Take-off): a closed run of separate sides is painted building INWARD whichever way round each side was drawn (the run's direction decides), but a side on its own builds to the right of its own travel, which is OUTWARD for a side drawn the other way round, so the band used for the doors and windows, the foundation centring and the selection outline of a side in a closed run uses the run's direction, not the side's (before this, a house drawn anticlockwise had its windows drawn on the outside of the wall and a bay projecting inside). **Deductions and the cavity wall**: every wall item carries the openings drawn on it (`TakeoffItem.drawnOpenings`, ids `po-…`, typed as the wall's own opening list `WallOpening` by `wallOpeningTypeFor`), kept in step by `withDrawnOpenings` (module level in Take-off `page.tsx`, called from `changePlaced`, so a place, drag onto another wall, edit, delete and undo all keep it right): an area-priced wall (unit m² with a gross `area`) has its net `qty` = gross less typed AND drawn openings (`openingsAreaOf`, also used by `recalcItemsForMpp` and both wall panels), an internal wall's per-m² materials are recalculated and un-confirmed, and the Openings section of the wall's Properties lists the drawn ones read-only (edited with the Place Window / Door tool, not there). A wall priced another way (a calculator, a unit that is not m²) keeps its own quantity. The CAVITY WALL calculator is fed the openings drawn on its wall (`wallOpenings` render option, `planWallOpenings` and `mergePlanWallOpenings` in `lib/wall-openings.ts`, tested; `CavityOpening` gained `planId`/`fromPlan`): each drawn opening is added at its distance from the wall's first end (offset = centre less half the width), a window with a 900 sill and a steel cavity lintel, a door with no sill, a bi-fold 3000 x 2100 under a steel beam, a garage door as a custom opening; it follows the drawing (position, size, kind) when the drawing's opening changes and is otherwise left as typed (so a lintel you chose stays), one deleted on the drawing leaves, and an opening typed in the calculator with no drawing is never touched. The calculator's own sample window is not added when openings are drawn on the wall. A wall priced earlier is NOT flagged out of date when openings are drawn afterwards: open its calculator and Save & Price again. Not built: other wall calculators with openings (timber frame etc.), walls of different make-up meeting at a corner, rooms made from the walls.

**Foundation lines are drawn at their real width, and any drawing can have its own colour** (Take-off & Draw): a line in the Foundations phase is painted as a band `foundationWidth` mm wide (600 until changed) to the plan's scale, centred on the line you drew, filled in the drawing's colour (28%), outlined in it (blue when selected), with a dashed centre line and a label `<name> · 600mm wide` (`renderElement`, the same `wallDrawing` band maths as walls with a one-layer spec). The width is edited in Properties (Width) AND in the strip / trench fill calculator: a width or depth changed in Properties is written into the saved calculator state (`withCalcNumber`, namespace `AssemblyStripFoundationDemo`, keys `widthMm` and `depthMm`) and the saved PRICE is cleared (it was made at the old size, so it must be Saved & Priced again; a toast says so), the calculator opens with the drawn width and depth (`basics`), and a width typed in the calculator and saved goes back to `foundationWidth` (the `size.widthMm` of the save, as the length does). The other foundation calculators on a line (piled, underpinning) have no width of this kind, and the other calculators with a drawn size (roof, floors, walls) already scale the drawing by their length, width or area (see 'A calculator's size carries back'). **Position under the wall**: a foundation is drawn centred on its line, but an external wall is drawn from its OUTSIDE face and builds inward, so the two are half a wall thickness apart. `TakeoffItem.foundationOffsetMm` sits the band sideways (positive = to the right of the way the line was drawn, the `offsetPolyline` convention; the line, its length and its quantities do not move), typed in Properties ('Position under the wall') or set by 'Centre under the nearest wall' (`foundationOffsetToWall`: the signed distance from the middle of the foundation's longest side to the centre line of the nearest wall drawn at real thickness within 1.5m, tested; a foundation along a 340mm cavity wall's outside line comes out at 170mm to the right when drawn in the same direction and -170 the other way round, the same place). **Colour on the plan** is in Properties for any drawing that has one (a section above Delete: twelve swatches, any colour, or back to the phase colour; it sets `DrawnElement.color`, which lines, rectangles and polygons are stroked in); a wall drawn at its real thickness has no colour to choose (it is painted in the usual colours of its materials).

**Strip foundation and trench fill (`fnd-strip`, `fnd-trench-fill`, one engine `lib/strip-foundation.ts`, screen `AssemblyStripFoundationDemo.tsx`)**: the wall up to the DPC now defaults to two 100mm block leaves with the cavity filled with concrete, built in COURSES (`coursing` on the input; brick course 75mm, block course 225mm, so 3 brick = 1 block): facing brick splash courses at the top of the outer leaf (default 3), block under them (worked out by default, or typed), the inner leaf block to the DPC. The courses decide the wall height: a shortfall to the DPC level is made up in the concrete thickness (never a low DPC), courses taller than the space put the DPC higher (both warned, and the DPC under 150mm above ground warns), and the section drawing shows every course with its dimensions. A saved calculator that was solid 215mm flat blocks stays that way; without `coursing` the engine is exactly as before (tested). The AI quote prices the new default (cavity, 3 brick courses).

**Cavity wall openings** (`calculateCavityGeometry` in `lib/assembly-calc.ts`, screen `AssemblyCavityWallDemo.tsx`): each opening is a window, door, BI-FOLD DOOR (starts 3000 x 2100 to the floor under a steel beam) or custom, with its own lintel: steel cavity lintel, two concrete lintels, concrete + angle, or a specified STEEL BEAM (a section from `STEEL_BEAM_SIZES`, priced per metre including 150mm bearing each end, with two padstones and a cavity tray; the section is the designer's, the calculator only prices it). An opening over 2.4m under a standard lintel warns. Every opening gets cavity closers down both jambs (`closerLm`) and, unless switched off, its INSIDE REVEALS finished: returns of plasterboard (with adhesive for dot-and-dab) or plaster over both jambs and the head at a typed depth (150mm), with angle bead and stop bead (`revealLm`, `revealAreaM2`). A cill or window board is not counted. The AI quote prices the same.

**A calculator's profit % is the sub-phase's margin, not a cost row.** When a calculator is saved into a quote (Save & Price, the AI quote, or Take-off
import) its "Profit (n%)" line is dropped from the quote items and its % is stored on the sub-phase as `QuotePhase.markupPct`; `calcPhaseSell` (and every
item-level sell) uses `phaseMarkup(p, quoteMarkup)`, so a calculator sub-phase takes ITS margin instead of the quote's overall markup (no double profit).
Margin means "% added on top of cost", shown as Cost (ex VAT) / Margin n% on cost / Sell (ex VAT). Never show a client the margin: client-facing views
go through `lib/client-items.ts` (folds any old "Profit" rows into the other rows and drops calculator cost-rate notes).

**Build it**
1. Engine: its own pure module — in `lib/assembly-calc.ts` for a wall/roof costed from drawn geometry
   (geometry + `calculate…Cost`, reusing `costLayer`; add its quantity-source type to the
   `AssemblyQuantitySource` union), or its own `lib/<name>-units.ts` for a calculator priced from a list of
   items rather than a drawn length/height (see `lib/rooflight-units.ts`: `priceRooflightItem` for one item's
   parts, a `resolve…Materials` that combines several into lines, `costLayer` called directly with
   `layer.fixedQty` as the raw quantity — no geometry object to thread through). A companion `lib/<name>-labour.ts`
   / `lib/<name>-description.ts` may live alongside an engine that already has one (`lib/flat-roof-labour.ts`,
   `lib/flat-roof-description.ts`) rather than each calculator inventing its own. Hand-work the numbers and
   test the engine (`node file.mts` with `file:///` import URLs) before building the screen.
   **Every `lib/*-description.ts` and `lib/*-labour.ts` module takes only *type* imports from the engine file
   it describes/costs** (`import type { … } from './x-units'`), never a runtime value import — this repo's
   extension-less relative imports (`moduleResolution: "bundler"`) can't be resolved by plain Node at
   `node --experimental-strip-types` test time, only by the bundler. If a description/labour function needs a
   label map or a pricing function from the engine, give it its own small local copy (see `KIND_LABEL` in
   `lib/rooflight-description.ts`, `KIND_PHRASE` in `lib/flat-roof-description.ts`) or have the caller (the
   screen, which has no such constraint) pass the already-computed numbers in.
2. Screen: `components/Assembly<Name>Demo.tsx`, props `{ onClose?, onSave?, labourTrades?, externalLengthMm? }`,
   built from `components/assembly-ui.tsx`. Must have: the materials print/CSV list (`MaterialsListButtons`),
   sample rates editable per line, labour section, misc materials, waste/profit, a quote description, and a
   drawing. An engine error is shown as a **banner above the controls — never instead of them** (typing a
   value digit by digit passes through invalid ones, and the controls must stay to correct it).
   **Defaults**: profit margin defaults to **20%** (`useState(20)` for `profitPct`), not 0. Optional extras the
   job may not have (rooflight openings, and anything similar in future calculators) start **empty/off** —
   never pre-seeded with a sample one — so the price starts at what's actually there and the estimator adds
   what the job needs. Every named block of properties (Build-up, Joists, Edges, Foundation, Piers, ...) is a
   `CollapsibleSection` (`components/assembly-ui.tsx`) — **collapsed by default**, so the panel opens showing
   only the length/height and the section headings, not every control at once. Never use a plain `<div>` +
   heading for a properties block again.
   Back Office's own **Assemblies list** (`app/(app)/back-office/components/SectionAssemblies.tsx`) follows the
   same rule: every phase group starts collapsed, whether or not it has a built calculator — don't special-case
   "phases with a built assembly start open" again.
   **Quote description is two-tier**: `onSave` passes a short one-line `description` (becomes the phase's
   `taskName`, printed everywhere) and may pass a full part-by-part `detail` (becomes `QuotePhase.scopeDetail`,
   shown on the online/HTML quote behind a "What's included" toggle and on paper only if "full descriptions"
   is ticked). Write both with pure functions in `lib/<name>-description.ts` (see `lib/flat-roof-description.ts`:
   `describeFlatRoofShort` / `describeFlatRoof`, tested) so they follow the inputs until hand-edited — never a
   snapshot taken when the calculator opens. `detail` is optional; a calculator with only `description` is fine.
3. Register: id in `lib/built-assembly-ids.ts` (`BUILT_ASSEMBLY_CANONICAL_IDS`), icon glyph + entry in
   `lib/built-assemblies.tsx`, and the sub-phase itself in `lib/phase-tasks.ts` (an existing sub-phase is just
   registered; a new one gets an entry in the right sub-phase array).

  `AssemblyFlatRoofDemo` with a `part` prop ('structure' | 'covering' | 'gutters'; 'complete', the old

  (`suggestFlatRoofLabour(…, scope)`) and description (`describeFlatRoof(…, part)`), and the parts' totals add
  up to the complete roof's. Mono-pitch/lean-to structure is its own component, `AssemblyMonoPitchRoofDemo.tsx`

  always, and a ledger+hangers or a wall plate+straps at the high wall (the same choice the flat roof offers
  at an existing wall), with a Swap button for length/span if the roof was drawn the other way round. Its
  rafter section reuses the flat roof's own span chart (`lib/flat-roof-joist-spans.ts`,
  `checkFlatRoofJoist`/`flatRoofSpanChart`), passing the roof's true sloped rafter length in as the span,
  rather than duplicating the span-chart physics. It also has its own roof-window openings — trimmed rafters
  (doubled/tripled) and a kerb, positioned in plan and draggable on a plan-view SVG (shown above the
  cross-section) — mirroring the flat roof's own opening system (`monoPitchRafterLayout`/`openingTrimZoneMm`
  in `lib/mono-pitch-roof.ts`, a self-contained copy of `flatRoofJoistLayout`'s logic): a member running
  parallel to the rafters (a side trimmer, or a kerb side up the slope) is true (sloped) length, one running
  parallel to the eaves (a header, or a kerb side across the slope) is horizontal and unscaled. The rooflight
  units themselves are still priced separately, under `roof-rooflights`. Gable structure is its own component,
  `AssemblyGableRoofDemo.tsx` (engine `lib/gable-roof.ts`, description `lib/gable-roof-description.ts`, labour
  `suggestGableRoofLabour` in `lib/flat-roof-labour.ts`) — two rafter faces to a ridge, a wall plate + straps
  at each of the two eaves walls (always standalone, no ledger option — a gable roof doesn't bear on an
  existing wall the way a lean-to does), and ceiling joists tying the rafter feet together across the full
  span; a new gable end wall is priced under External Walls, not here. Its rafter section reuses
  the same span chart the same way (true sloped length = half the span plus the overhang, over cos(pitch));
  ceiling joists get a section picker but no span-chart check (a long span needs a binder or an engineer's
  design — noted, not modelled). No roof-window openings yet (mono-pitch's plan-view/trimmer pattern in
  `lib/mono-pitch-roof.ts` is ready to reuse there when asked). Each of the gable roof's two ends is
  independently `'gable' | 'existing-wall'` (`GableEndTreatment`), same real case as the hip roof's per-end
  treatment (a rear extension tied into the house at one end). Unlike hip, a gable end never got a wall-plate
  credit either way (that was already true before this — the new wall's own top plate is its own build's
  scope), so `'existing-wall'` only *adds* restraint straps tying the ridge and end rafters back to it — the
  default (both `'gable'`) case is priced byte-for-byte the same as before this was added, confirmed by
  re-running the original hand-test unchanged. Rafter/ridge framing is identical for either end treatment
  (the ridge always runs the full length on a gable roof, unlike a hip's). Hip structure is its own component,
  `AssemblyHipRoofDemo.tsx` (engine `lib/hip-roof.ts`, description `lib/hip-roof-description.ts`, labour
  `suggestHipRoofLabour` in `lib/flat-roof-labour.ts`) — common rafters along the ridge zone on the two long
  sides, four hip rafters at 45° from each corner to a ridge end, jack rafters filling each hip triangle, a
  wall plate + straps round the full perimeter (every wall is an eaves wall on a hip roof — no gable ends to
  price under External Walls here), and ceiling joists across the full length. If the span is at least as
  long as the ridge-direction length the ridge length comes out at zero — a pyramid hip, no ridge board, the
  four hips meeting at a single apex instead; the engine and screen both handle this without a special case
  breaking (`isPyramid` flag, checked everywhere a ridge would otherwise be priced or drawn). The roof surface
  is one uniform pitch everywhere (commons, hips and jacks all lie in the same sloped planes), so the slope
  area is simply the overhung plan area over cos(pitch) — no need to sum every rafter's own strip, and a
  cleaner formula than the flat/mono-pitch/gable roofs use, worth carrying back to them if they ever need it.
  A jack rafter shares its roof plane's pitch with the common rafters it's parallel to, so it uses the very
  same true-length formula, just with its own (shorter) distance in from the corner as the run; a hip rafter's
  own run is on the diagonal (a 45° hip, stretched by √2), reaching the same rise, so its length comes from
  Pythagoras rather than the roof's pitch angle directly. Only the common-rafter length is checked against the
  span chart; hip and jack rafters (and the ridge board) take the next timber size up, same convention as the
  ledger/kerb sizing elsewhere. No roof-window openings yet, same as gable.

  **Pitched roof covering** (`roof-covering`'s `pitched` family, `AssemblyPitchedRoofCoveringDemo.tsx`, engine
  `lib/pitched-roof-covering.ts`, description `lib/pitched-roof-covering-description.ts`, labour
  `suggestPitchedRoofCoveringLabour` in `lib/flat-roof-labour.ts`) is a different pattern from every other
  covering/structure calculator: `lib/pitched-roof-covering.ts` itself is roof-shape-agnostic — it only takes
  already-worked-out edge lengths (slope area, ridge/hip/verge/abutment/eaves lm) and adds the one covering-
  specific number, the batten run (`slopeAreaM2 × 1000 / gaugeMm` — an area/gauge identity that holds for a
  hip's trapezoidal faces too, not just a plain rectangle, since a batten course's length is proportional to
  local face width and courses are evenly spaced). Which roof type (mono/gable/hip) and which per-end choice
  gives which edge lengths is worked out by the **screen**, calling `calculateMonoPitchRoofGeometry`/
  `calculateGableRoofGeometry`/`calculateHipRoofGeometry` **directly at runtime** — screens have no
  type-only-import restriction, only `lib/*-description.ts`/`lib/*-labour.ts` modules do, so this is fine and
  reuses the already-tested structure trig rather than re-deriving it a third time. The mapping: a ridge only
  exists for gable/hip; a hip cap follows the hip rafters' own line (`hipRafterLm`, reused directly); a verge
  runs up the slope (the true rafter length) at any new-wall gable end, or a hip's non-hipped `'gable'` end;
  an abutment (lead flashing) runs wherever the roof meets an **existing** wall instead — always at a
  mono-pitch's high wall (whichever way it's fixed there), or any gable/hip end set to `'existing-wall'`;
  eaves are simply wherever the structure's own geometry credits a wall plate (`wallPlateLm`, or `lengthM` for
  mono's one low wall) — "eaves" and "gets a wall plate" are the same thing in every one of these engines, so
  it's reused rather than re-derived. If a future covering calculator needs the same shape-agnostic-engine
  pattern, this is the one to copy — not the structure calculators' own self-contained-engine pattern. Each of the hip roof's two ends
  (along the ridge direction, not the long eaves) is independently `'hip' | 'gable' | 'existing-wall'`
  (`HipEndTreatment`) — a real case: hipped at the garden end, tied into the house at the other. A gabled or
  existing-wall end gets no hip/jack rafters at all (the ridge and common rafters simply run the full way to
  it, exactly like a gable roof's), and only an existing-wall end skips the wall-plate credit there (nothing
  new is built — still gets restraint straps back to it, same as every other end). Both ends non-hip and the
  ridge runs the full length, same numbers a gable roof would give for that length/span — a good consistency
  check when extending an engine like this. `isPyramid` only applies when *both* ends are `'hip'` and the
  ridge would go to zero; a single hip end reaching zero (too short a length for even its own half-span) is a
  different, genuine problem, warned separately. `roof-structure`'s "Include fitting the rooflights" optional
  labour line points the estimator at `roof-rooflights` instead of duplicating it — a new calculator that also
  fits something another one prices should do the same, not silently double-count. `roof-structure` pairs with
  the `cold_flat_roof`/`warm_flat_roof` Build-Up Types (flat only so far); the others appear under
  "Calculators". A roof is sized from the bounding box of the drawn shape via `drawnBoxMm`, passed as
  `externalLengthMm` + `externalWidthMm`, and the panel card shows "Size" not "Length" — `roof-rooflights`
  ignores both (it has no drawn geometry; any small shape drawn for it is just a placemarker). A calculator
  for any other phase (floors, plastering, ...) needs
  `resolveBuiltAssembly`, the properties panel's Build-Up Type/sub-phase picker, the `hideForBuiltAssembly`
  flag, and the carry-over extended to that phase — do it the same way, don't fork a new pattern.

## Take-off sheets: several plans in one take-off (REQUIRED if you touch `app/(app)/takeoff/page.tsx`)

## A calculator's size carries back to the Take-off drawing (REQUIRED for a new drawn-size calculator)

A calculator is sized from the drawing (a line's length, a roof's box, a floor's area) and, when the estimator types a different size inside it and presses Save & Price, the DRAWING is scaled to match so the quantity, label, area and schedule agree (it used to change only the price). `CalcScope` (`components/calc-state.tsx`) stamps each state namespace as it is written and hands the save handler `size` (`CalcSize`, `sizeFromValues` in `lib/calc-size.ts`): the namespace with a `lengthMm` or `areaM2` written most recently (a roof switched between types leaves the old type's values behind), reading `lengthMm`, `widthMm` (or `spanMm`: gable, hip, mono-pitch and pitched covering call their width a span) and `areaM2`. In Take-off's `renderAssemblyPanel` onSave, `planResize` / `applyResize` scale the item's element by what kind of drawing it is: a LINE by its length from its first point, a BOX (roof, raft: `isBoxShape`) so its bounding box becomes the calculator's length and width (the long side stays the long side), a FLOOR (`isFloorShape`) evenly to the calculator's area; then `recalcItemsForMpp` re-measures that one item and a toast says what changed ("8.00 × 4.88 m → 10.00 × 4.88 m"). Within 0.2% nothing moves. So a new drawn-size calculator must keep its drawn size in a `useCalcState` named `lengthMm` (and `widthMm`/`spanMm`) or `areaM2` to take part. Not covered: the tiling and other room-by-room calculators (their sizes live inside rooms), calculators that take no drawn size (Wall Removal, Render and Wall Insulation keep their length in a list of walls), and the electrics path.

## Take-off drawing aids: undo/redo, snap, ortho, typed lengths, copy, rotate (REQUIRED if you touch the drawing handlers in `app/(app)/takeoff/page.tsx`)

Pure, tested modules: `lib/takeoff-snap.ts` (`anchorsFor`, `snapPoint`, `parseTyped`, `pointAtDistance`, `rectCornerAt`, `rotateShape`) and `lib/takeoff-history.ts` (`observe`, `undoStep`, `redoStep`). **Snap** (🧲, on by default): the cursor snaps within 10 SCREEN pixels (`10 / zoom` in plan pixels) to the corners and ends of the drawings on the showing sheet (a rectangle is stored as two opposite corners: `cornersOf` gives its four), the middle of each side (a corner wins over a slightly nearer mid-point) and the points of the shape being drawn; a dragged vertex snaps the same way. **Ortho** (⊾, or hold Shift for one line): with a previous point the new one is locked horizontal or vertical from it, and a corner near the locked line is snapped to ALONG it. Everything that places a point goes through `drawingPoint(raw)` (mouse move sets `mousePos` from it, so the ghost shows the snap; the click handlers call it again), so a new drawing tool must use it too. **Typed lengths** while drawing a line, polygon, floor or rectangle: digits, '.', 'x' or ',' collect in `typed` (box at the bottom of the canvas); Enter places the next point that many metres from the last, the way the cursor points (so with Ortho on it runs straight); '4.5x3' completes a rectangle running the way the cursor is; Enter on its own finishes (the same as a double-click); Backspace takes back a typed digit, then the last point (and no longer deletes the selected drawing while drawing). **Undo / redo** (Ctrl+Z, Ctrl+Y or Ctrl+Shift+Z, buttons): while drawing, undo takes back the last point; otherwise it steps through the take-off's `elements` and `items` (so a priced item, a calculator save and its resize, a delete and a paste all undo together); a burst of changes within 600ms is ONE step (a drag), 80 steps kept, redo is cleared by a new change, and the history starts again when the take-off or its sheets change (a deleted sheet's drawings must not come back without the sheet). It does not cover the scale, the sheets themselves, or the plan picture. **Copy** (Ctrl+D, ⧉): copies the selected drawing and its item (not the electrics item) 30 screen pixels down-right and selects it. **Delete / Backspace** removes whatever is picked, one thing at a time: a picked electrical point (`selectedElectricPointId`; picking a point lets go of the drawing and opening, and picking a drawing or opening lets go of the point, so Delete never removes something picked earlier), else a placed door or window, a room edge, a drawn room, or the picked drawing (every drawing, including a Click-to-place item, a pipe line and a drain run, is picked with `selectedId`). **Escape** cancels what is being drawn (points, typed length, measure, calibration) AND puts the cursor back on Select (`Esc` in the keyboard handler; a toast says so), so a finished line never starts the next one; with a menu open it only closes the menu, and in a text box it leaves the tool alone. **Rotate** (⟳, or R for a quarter turn): turns the selected drawing clockwise about the average of its corners; a rectangle turned a quarter turn stays a rectangle, turned any other angle becomes a four-cornered polygon; the item is re-measured (`recalcItemsForMpp`). **Snap to grid** (▦ Snap to grid beside Grid in the Draw group, with a spacing of 100mm, 250mm, 500mm or 1m, kept per browser as `gridSnap` and `gridStep` in `sbc_takeoff_view`; turning it on also shows the grid): `snapPoint` takes `grid: { stepPx }` and, when no corner or end is within the snap radius, rounds the point to the nearest grid crossing counted from the plan's top left corner (kind `'grid'`, a blue cross marker); locked to ortho only the free coordinate goes to a grid line; a corner of another drawing still wins when the cursor is right on it; it works without the corner snap and a dragged corner snaps to it too. The grid lines and the snapping always agree: `gridMinorPx` is the chosen step, or a multiple of it (2, 5, 10, 20, 50, 100) when it would be under 8 screen pixels at the current zoom, and the major lines are every fifth. The grid is not a real-world datum (it starts at the plan picture's corner), and typed lengths ignore it. **Snap onto a wall** (kind `'edge'`, an orange ring): with Snap on, when no corner or end is within the snap radius the point goes onto the nearest SIDE of any wall on the sheet, anywhere along it (`segmentsFor`, the `segments` option of `snapPoint`; a corner or end still wins, and the grid applies only when no wall is near); with Ortho locked it lands where the locked line crosses the wall, and a locked line parallel to the wall does not snap to it. This is how an internal wall is ended exactly on an external wall (a tee: the external wall is painted over it). **An internal wall snaps to the INSIDE face of the external walls** (`insideFaces` in Take-off, tested): while an internal wall is being drawn (or one of its ends dragged) the external walls are not snapped to along the line they were drawn on (their outside face) but along their inside face, taken round each run of joined external walls (`wallBand` and `offsetPolyline` of the chain, so the corners are the true inside corners of the room, also offered as end snaps), so a partition ends flush with the inner skin; every other kind of drawing still snaps to the drawn line. **Joined walls move together** (`lib/wall-links.ts`, tested; `buildDragLinks`, `applyLink`, `linksForDrag` in Take-off): when a wall (or one of its corners) is dragged in Select mode, every other wall that has a point within 3 plan pixels of it comes along, so a corner stays a corner and the neighbour stretches or shrinks; moving a whole wall also carries the END of any open wall that lands on one of its sides (a tee) by sliding it along its own direction to the moved wall's new line, so a partition stretches to stay on the wall (a corner drag changes the angle of two sides, so tees are left alone); walls that are rectangles are not linked; an INTERNAL wall never carries an external wall with it (a partition only meets the outside walls: it is joined to other partitions only), while an external wall carries the partitions joined to it; hold ALT when you start the drag to move a wall on its own; the walls joined to a dragged corner are not snapped to; lengths are re-measured at the end of the drag as for any move. **Join Corner** (the ⌐ tool in External Walls and Internal Walls & Partitions; `joinCorner` in `lib/wall-links.ts`, tested; `joinClick` in Take-off): click one wall near the corner (it is picked out in orange), then the other; the two sides that were clicked are extended or trimmed so they meet exactly where their lines cross, moving the end of each that is nearer the crossing (an overshoot is trimmed back, a gap closed), and the walls already joined to those ends come along (the same links as a drag). Parallel walls never meet, and if an end would have to move more than 3 m the walls are not one corner (both said in a toast); a wall that is a rectangle or polygon must be split into separate walls first; two sides of the SAME wall cannot be joined with it. It is undoable and stays on so several corners can be joined; lengths are re-measured as for any move. Not built: alignment guides, perpendicular/tangent snaps, moving by a typed distance, mirror, scale-by-factor, multi-select.

## Walls drawn at their real thickness, layer by layer (Take-off & Draw)

A wall in External Walls or Internal Walls & Partitions is painted architecturally: a band at its REAL thickness to the plan's scale, made of its layers in the usual conventions (facing brick = red diagonal hatch, block = grey dots, insulation = yellow zig-zag, cavity = white, timber = brown cross, boards and render thin), labelled in its tag ("300 cavity", "215 solid block", "100 stud partition"). Pure module `lib/wall-drawing.ts` (tested): `wallSpecForItem` in `app/(app)/takeoff/page.tsx` decides WHAT the wall is, in this order: (1) its saved calculator (`assemblyCalcState`: the cavity wall's outer leaf, cavity, insulation and inner leaf via `cavityWallSpec`; a solid block's width or flat 215 via `solidBlockSpec`), (2) its Build-Up Type's own layers (`allWallMakeups`: the live Back Office wall type, read by `specFromMakeupLayers`, which sorts layers into kinds by their names and gives a partial-fill layer the 25mm air gap a real cavity has), (3) the standard for its sub-phase (`defaultWallSpec`, a cavity wall with nothing else known being drawn INSULATED as the calculators start: full fill is brick + 100 mineral wool + block, partial fill is brick + 75 PIR + 50 air gap + block; a saved calculator's own `boardThicknessMm` sets the PIR thickness and the rest of the cavity is the gap; checked by eye on a sheet of every wall type 2026-10-28: stud, metal stud, block partition, 100/215 blockwork, timber garden room, dwarf and sleeper walls), else nothing and the old fixed-pixel band is used. An external wall with no type picked shows the first type, as the Properties panel does. WHERE it sits: external walls take the line you draw as the OUTSIDE face and build to the inside (the right of the way you drew; for a rectangle or polygon outline towards the middle, whichever way round it was drawn; "⇄ Flip to the other side" in Properties, `wallFlip`, for an open line drawn the other way); internal walls are centred on the line. `wallDrawing` gives each layer as an SVG path (mitred corners, two rings for a closed outline, fill-rule evenodd); the screen paints them in `renderElement` (after the layer is wide enough on screen, 3px, the hatching shows; narrower it is a plain tinted band), a white halo behind in `renderHalo`, and the hatching patterns are `wl-*` in the SVG defs (scaled by 1/zoom so they stay the same density). Quantities are unchanged: they still come from the drawn line's length (the outside face for an external wall). **Where walls meet** (`chainWalls` in `lib/wall-drawing.ts`, tested; painted by `renderWallVisuals`, which paints ALL the walls after the element loop with pointer events off, while `renderElement` keeps only each wall's clicking path): walls of the same group (external/internal, reference, and the same layers) whose ends meet within 3 plan pixels (snapping makes them exact) are one run with mitred corners, a flipped wall being taken from its other end so the inside is always to the right, and a run that comes back to its start is a closed ring (four separate walls round a house paint as one ring, built inward). **Near corners are painted as corners** (`reachPx` on a `WallPiece`, set by `renderWallVisuals` and `wallSolids` to 1.5 wall thicknesses, tested): two open walls of the same make-up whose ends stop SHORT of the point where their lines cross (up to 1.5 thicknesses away: a gap, or a wall drawn to the face of the other), or run PAST it (an overshoot, up to HALF that), are painted as meeting exactly at that crossing, so the skins (brick, insulation, inner block) run continuously round the corner instead of one wall butting into the other; a wall that carries on well past the crossing is a tee and is left alone, as are walls too far from the crossing, parallel walls and walls of different make-up. Only the PAINTING (and the room finding, which uses the same chains) changes: the walls' own lines and lengths are not, and the Join Corner tool makes the geometry itself exact. A wall ending on the SIDE of another is not joined: internal walls are painted first and external over them, and within a kind the longer wall over the shorter, so a partition stops at the face of the wall it butts into (the clean look of a T-junction). The selected wall's blue dashed outline is painted last, over everything. Walls of different make-up meeting at a corner (a cavity wall and a solid block wall) are not joined and overlap. **One wall per side**: a wall drawn as one run (three clicks or more with the Line tool: the U of an extension) is split into ONE WALL PER SIDE when it is finished in External Walls or Internal Walls & Partitions (the 'Each side of a wall is its own wall' tick under the tools, kept per browser as `splitWalls` in `sbc_takeoff_view`, on by default), so each side is its own drawing and its own Take-off item that can be clicked, edited, priced with its own calculator and doors and windows, and deleted; because walls of the same make-up whose ends meet are painted as one run (`chainWalls`), the drawing looks the same. An existing wall drawn as one run (or a rectangle or polygon wall) is split from its Properties ('✂ Split into N separate walls', `splitWallSides`, undoable): `lib/wall-split.ts` (tested) gives the sides (`sidesOf`: a rectangle's two corners become four sides, closed) and moves the placed doors and windows onto the side they were on (`splitOpenings`); each side keeps the wall type, height and sub-phase, the typed openings go to the first side, and the saved calculator and its price are CLEARED (the length has changed, so each side must be opened and Save & Priced again; a calculator's own settings start from the wall type again). A single two-point line is never split, and walls drawn before this change stay as they were until split. Not built yet: doors and windows in the band, rooms made from the walls, and a printed plan; timber frame and other wall calculators use the build-up layers or the sub-phase standard, not their own sizes.

## Rooms made from the walls (Take-off & Draw)

Rooms are FOUND, not drawn. `lib/rooms-from-walls.ts` (pure, tested) `detectRooms` fills in every wall (the rings of `wallDrawing(...).rings`, joined where walls meet exactly as they are painted, `wallSolids` in Take-off) AND the gap of every placed door and window (so an opening never joins two rooms) on a 10mm grid (bigger cells only for a huge drawing), then the empty space that does not reach the edge is a room: its outline (cell edges walked round and simplified, so a rectangle is four corners and an L six), floor area (cells, less a column or chimney breast standing in it), the length of wall round it, the box it fits in, and where its name goes (the roomiest cell). A room is only found if its walls make a closed space: a gap shows as no room, and the Rooms panel says so. Rooms are re-found 250ms after the last change to walls, items or openings (not on every mouse move of a drag) and only while shown (the Rooms tick in the view box top right, the 🏠 Rooms tool, or a calculator open), and ignored if the sheet has changed meanwhile. The doors and windows that open into each room are counted by looking 150mm beyond each face of each opening (a door between two rooms counts in both).

**Drawn rooms**: a room with no walls round it can be DRAWN as a shape: with the Rooms tool on, pick Rectangle or Polygon in the tool list (or the 'Draw a room' buttons in the Rooms panel; typed sizes like 4.5x3 work as for any rectangle) and `finishElement` hands the outline to `addDrawnRoom` instead of making a priced drawing (`roomDraw`, reset whenever the tool is not rectangle or polygon). It is stored as a `DrawnRoomShape` (just the outline) in `TakeoffSheet.roomShapes` (on the project, `TakeoffProject.roomShapes`, before there is a sheet; both moved onto the first sheet by `addSheets`, and carried in the cloud `calibration` meta) and joins the rooms found from walls (`roomFromPolygon`, `sortRooms`; a drawn room has `drawnId`, no openings are counted for it unless a placed opening happens to sit beside it, and it can be deleted from the panel; it can be MOVED (drag it by its middle with the Rooms tool on), RESHAPED (drag a white corner of the selected room; a rectangle, `DrawnRoomShape.rect`, stays a rectangle, held to the opposite corner, and the corner snaps like any drawn point) or RESIZED by typing its width and depth in the panel (its top-left corner stays); the pure rules are `moveOutline`, `rectFromCorners`, `resizeRectOutline`, `isAxisRect` and `labelAfterEdit` in `lib/rooms-from-walls.ts` (tested), and the room's name point moves with it (or is brought back inside if a reshape leaves it outside). Drawn rooms are added to the room list fresh on every render (`roomData`), while the rooms found from walls come from the debounced `roomCore`, so dragging one is smooth. Moving and resizing drawn rooms is not part of undo). A shape drawn with an ordinary phase's rectangle tool (Floors & Screeds, etc.) is NOT a room. **Room edges**: a ROOM EDGE is a line that closes a room where there is no wall (the open side of three walls, an extension against the existing house) or splits an open-plan space into rooms; it is not a wall, so nothing is painted, priced or counted for it. With the Rooms tool on, pick Line in the tool list (or 'Room edge' in the panel; `roomDraw` is `'room' | 'edge' | false`) and click its start and end (double-click to finish; a bent edge works). It is stored as a `RoomEdge` (a list of points) in `TakeoffSheet.roomEdges` (project-level `roomEdges` before there is a sheet, moved onto the first sheet by `addSheets`, carried in the cloud meta like `roomShapes`), shown dashed purple with the rooms, and passed to `detectRooms({ edges })`, which fills each segment in as a strip one and a half cells wide AFTER the cell size is known (so it always closes the gap, even slanted; it takes about 15mm of floor along its length) and includes it in the drawing's box; edges alone make no room, they only close what walls make. Click an edge with the Rooms tool to select it; Delete or the panel's Delete removes it. **A drawn room that walls now surround is left out** (`roomData.coveredDrawn`): a drawn room whose name point is inside a room found from walls (or the other way round) is the same room twice, so the room the walls make wins (measured between the wall faces), the drawn piece is dropped from the list, the plan labels and the calculators, and the Rooms panel says so with a button that removes the leftover outlines (the names stay: they belong to the rooms the walls make). **An edge also CUTS A DRAWN ROOM** (`splitDrawnRoom`, `edgesTouch` in `lib/rooms-from-walls.ts`, tested): a drawn room crossed by room edges (right across it, or a line between two corners of its outline, such as the line between the two blocks of an L) becomes the pieces the edges make of it, each a room that can be selected, named and fed to the calculators; the outline and the edges are filled in as thin strips and the enclosed space found (`detectRooms` with `edgesMakeRooms`, which gives the strips' half-width back to each piece's area), only when an edge actually touches the room and makes two or more pieces (otherwise the exact outline is used); each piece keeps the shape's `drawnId`, so moving, reshaping, resizing (the whole rectangle) or deleting acts on the drawn shape and every piece's name goes with it (`editDrawnShape` moves EVERY name inside the old outline); the shape's grab area and corner handles are the shape's, drawn from `roomShapesOf`, not each piece's. The edges do not move when the shape is moved. Edges cannot yet be moved or reshaped (delete and redraw). **Names** are `RoomLabel`s on the SHEET (`TakeoffSheet.roomLabels`, so they ride in the calibration JSON like the sheets, no SQL, and go with a deleted sheet): a name, a kind (`ROOM_KINDS`), a ceiling height (2.4m when not given), anchored to a POINT inside the room, so it follows the room if the walls change; the room that contains the point has the name (the first, if several). Unnamed rooms are "Room 1..." with an id from where they are. Naming is not part of undo. The 🏠 Rooms tool (any phase) selects a room by clicking inside it and opens `app/(app)/takeoff/components/RoomsPanel.tsx` (list with area, size, wall length, doors and windows; name, kind, height; wall area less openings). A point placed in the Electrics phase takes the name of the named room it falls in (`electricRoomShapes`).

**Handing rooms to the by-room calculators**: `PlanRoomInfo` (`describeRooms`) goes to the calculator as the render option `planRooms`; `components/PlanRoomsBar.tsx` shows them at the top of the calculator's rooms (press one to add it, or Add all); a calculator room made from one carries `planRoomId` and `planRoomSig` and FOLLOWS the plan (`followPlanRooms` in `lib/rooms-merge.ts`, tested: refit only when the plan's room changes, so what was typed stays; a room whose plan room is not found is left alone, never dropped or detached). Built so far: Internal Plastering & Boarding (by room) (floor and wall length from the true area and perimeter, `sidesFromAreaPerimeter`; height, doors, windows; the wall and ceiling areas overridden with the drawn ones) and Floor Tiling (by room) (an 'other' shaped room with the true area and perimeter, so an L-shaped room measures right, and its doors). Kind maps are `plasterKindFor` and `tilingKindFor`. Also fed the same way now: **Tiling Preparation** (true floor area and wall length as an 'other' shape, height; the wall areas to prepare start as the kind's usual ones; a shower room's floor is tanked), **Electric Underfloor Heating** (true area and wall length; the heated area is that less fixed things and the margin), **Wall Tiling** (name, true ceiling height and the kind's usual tiled areas: the plan cannot say which walls are tiled, so the areas are still set in the calculator and only the height follows the plan) and **Internal Decoration** (as plastering: size from the true area and perimeter, height, doors, windows, drawn wall and ceiling areas). **Strip-Out by Room** (floor area and height from the plan; what is taken out starts as the usual for that kind and size, and when the plan's room changes the items still at the usual for the OLD size move to the usual for the new one while any count you typed stays; `stripKindFor`) and **Plumbing Installation (by room)** (the name and kind with the kind's usual fittings only: a plumbing room's fittings do not depend on its size, so it remembers `planRoomId` but has nothing to follow; `plumbingKindFor`) are fed too. **Electrics** (`elec-install`) is fed too, beside its own point feed: the calculator takes `roomsOnPlan` (the `planRooms` render option) and shows the bar; a room added from it has the room's name and the usual points for its kind (`electricsKindFor`) and is tied to the plan by name (`planName`, `planRoomId`), so points placed on the plan in a room of that name COUNT IN it (their counts replace the usual ones for those kinds of point, no duplicate room is made) and a room already made by a placed point is shown as added. A point placed in the Electrics phase takes the name of the named room (found or drawn) it falls in. NOT yet fed: rooms across more than one sheet (rooms work on the showing sheet only). For any further by-room calculator add the same three pieces: a `planRoomId`/`planRoomSig` on the room type, an add function and a follow effect, the bar.

## Portal sign-in (subcontractor and client): an emailed 6-digit code, no password

## New database tables need explicit grants (REQUIRED, from 30 Oct 2026)

Supabase stopped automatically granting Data API access to new tables in the `public` schema on 30 October 2026. A table created without
grants returns "permission denied" to supabase-js and the app, which looks like a feature that silently won't save or load. So every SQL file that
`create table`s in `public` must, in the SAME file, also:
1. `grant select, insert, update, delete on public.<table> to authenticated;` and `... to service_role;` (add `grant usage, select on` any sequence it uses).
2. Grant `select` to `anon` ONLY if the table is meant to be readable when signed out. Most are not (nothing sensitive to `anon`). Decide per table.
3. Keep `enable row level security` and its policies as before: the grant opens the door to the API, the policies still decide which rows.
Tables created before 30 Oct 2026 keep their access, so old SQL files are left alone. `supabase/job-selections.sql` is a good example to copy.
If a database is ever rebuilt from the SQL files (new project, preview branch, `supabase db reset`), the older files that lack grants need a one-off pass first.
